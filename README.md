# OrangeHRM Test Automation Portfolio

## 프로젝트 배경

더존비즈온에서 CRM QA를 담당하면서, 고객관리나 프로모션 기능을 검수할 때마다 같은 시나리오를 손으로 반복하면서 회귀 테스트 자동화의 필요성을 느꼈습니다. 다만 사내 서비스는 보안상 그대로 공개할 수 없어서, 등록/조회/수정/삭제(CRUD)와 검색, 파일 첨부처럼 실무에서 다뤘던 기능 단위를 재현할 수 있는 대상을 찾다가 OrangeHRM을 선택했습니다.

## 왜 이 대상을 선택했는지, 왜 자체 호스팅까지 갔는지

- OrangeHRM은 CRM과 화면 구성이나 상세 기능은 다르지만, 데이터를 등록하고, 화면 전환 후 값을 채우고, 검색으로 재조회하고, 파일을 첨부하는 등 QA 자동화에서 반복적으로 검증하는 기본 동작 단위를 재현할 수 있었습니다.
- 처음엔 공개 데모(opensource-demo.orangehrmlive.com)를 썼는데, UI 언어가 바뀌어 버리는 등 공유 환경의 불안정함을 겪었습니다. 이후 Docker로 완전히 격리된 자체 환경으로 옮겼습니다.

## 아키텍처

```
project/
├── models/
│   └── employee.ts
├── pages/
│   ├── basePage.ts          # 공통 로케이터 전략, 로딩 대기, 입력+검증 유틸
│   ├── loginPage.ts
│   ├── adminPage.ts
│   ├── pimPage.ts
│   └── jobSettingsPage.ts
├── utils/
│   └── formHelpers.ts       # 드롭다운/입력그룹 셀렉터 로직 (BasePage와 global-setup.ts가 공유)
├── testData/
│   ├── seedData.ts          # 여러 파일이 공유하는 문자열 상수
│   ├── filePaths.ts         # 테스트용 파일 경로 상수
│   └── assets/              # 업로드 테스트용 실제 파일
└── tests/
    ├── admin.spec.ts
    ├── pim.spec.ts
    ├── jobsetting.spec.ts
    ├── login.spec.ts
    └── api.spec.ts
global-setup.ts               # 테스트 실행 전 설치 마법사 + 기준 데이터 시딩 자동화
docker-compose.yml
tsconfig.json
```

Page Object Model을 쓴 이유는 단순합니다. 동일한 셀렉터를 사용하는 구간이 많아 화면이 바뀌었을 때 고칠 곳을 페이지 클래스 한 곳으로 모아두고 싶었습니다. 셀렉터는 라벨 텍스트 기반(`getInputGroup`)으로 통일해서, 화면상 필드 순서가 바뀌어도 테스트가 쉽게 안 깨지도록 설계했습니다.

## 테스트 전략

| 파일 | 시나리오 |
|---|---|
| `admin.spec.ts` | 신규 시스템 유저 등록 → 목록 반영 확인 → 삭제 |
| `pim.spec.ts` | 신규 직원 등록 → 개인정보/연락처/직무정보(파일 첨부 포함) 저장 → 검색 → 삭제 |
| `jobsetting.spec.ts` | Job Title 등록(파일 첨부 포함) → 수정 |
| `login.spec.ts` | 로그인 실패 네거티브 테스트 |
| `api.spec.ts` | Job Titles 목록 API가 UI로 등록한 시드 데이터를 반환하는지 검증 |

실행할 때마다 유니크한 데이터(`Date.now()`, timestamp 조합)를 써서 재실행 시 충돌을 막고, 테스트가 끝나면 만든 데이터는 스스로 정리합니다. Job Title/Category처럼 여러 테스트가 전제로 삼는 값은 `global-setup`에서 한 번만 시딩하고, 이미 있으면 건너뛰는 멱등성 체크를 넣어뒀습니다.

## CI/CD

- Push, PR, 수동 실행 시 GitHub Actions에서 Docker Compose로 OrangeHRM과 MariaDB를 완전히 빈 상태로 띄웁니다.
- Playwright의 `global-setup.ts`가 테스트 실행 전에 설치 마법사(DB 연결, 조직 정보, 관리자 계정 생성)와 기준 데이터 시딩(Job Title/Category)까지 자동으로 끝내둡니다.
- 관리자 계정 정보는 GitHub Secrets로 주입하고, 로컬은 `.env`로 관리합니다.
- 컨테이너가 실제로 응답 가능한 상태인지 폴링으로 확인한 뒤 테스트를 시작합니다.
- 실패하면 스크린샷, 비디오, 트레이스를 아티팩트로 자동 업로드합니다.
- 최근 실행 결과 리포트: https://ahnintaek.github.io/auto_orangeHRM/

## 트러블슈팅

### 1. 공유 데모 환경의 불안정성
- 문제: 다른 사용자에 의해 공개 데모 사이트의 UI 언어가 스페인어로 변경되어 텍스트 기반 셀렉터가 전부 실패
- 해결: Docker Compose로 격리된 자체 환경으로 전환하여 재발 원천 차단

### 2. 비동기 폼 로딩으로 인한 간헐적 입력 실패
- 문제: Contact Details 등록 시 입력값이 저장 시점마다 다른 필드에서 랜덤하게 사라지는 현상 발생 
- 원인 분석: 화면 진입 직후 기존 데이터를 불러오는 API 응답과 Vue의 비동기 DOM 패치가 끝나기 전에 입력을 시도하여, 패치 타이밍에 걸린 필드의 값만 덮어써짐
- 해결: API 응답 대기(`waitForResponse`) + 로딩 오버레이(`.oxd-form-loader`) hidden 대기를 결합해 폼 완전 준비 시점을 명시적으로 확보하고, 입력 직후 값 검증에 실패하면 1회 재입력하는 `fillAndVerify` 유틸을 BasePage에 공통화하여 안전망으로 추가

### 3. 설치 상태를 이미지에 굽는 방식의 한계와 방향 전환
- 시도: CI에서도 설치 마법사 없이 바로 실행되도록, 설치가 끝난 앱 파일을 `docker cp`로 추출해 커스텀 Dockerfile에 포함시키는 방식을 시도
- 문제: 파일 복제 과정에서 권한/설정 정보가 일부 유실되어 HTTP 500 에러 발생, 원인 규명에 시간 대비 효율이 낮다고 판단
- 방향 전환: 파일을 복제하는 대신, Playwright의 `globalSetup` 훅으로 설치 마법사 자체를 자동화하는 방식으로 전환. 테스트 대상 앱의 초기화까지 Playwright로 자동화한다는 관점으로 접근을 바꾸니 기존 셀렉터 설계 원칙을 그대로 재사용할 수 있어 오히려 더 단순하게 해결됨

### 4. CI 환경에서 설치 자동화 스크립트의 headless 미설정
- 문제: `playwright.config.ts`에는 `headless: !!process.env.CI`로 환경별 분기를 해뒀으나, `global-setup.ts`는 별도로 `chromium.launch()`를 호출하는 독립 스크립트라 이 설정이 적용되지 않아 CI에서 "Missing X server" 에러로 실패
- 해결: `global-setup.ts`에도 동일한 `!!process.env.CI` 분기를 적용
- 배운 점: 환경별 설정은 한 곳에 모아 관리하지 않으면, 새로운 진입점이 생길 때마다 같은 실수가 반복될 수 있음

### 5. CI(headless) 환경에서만 발생한 반응형 레이아웃 이슈
- 문제: 로컬은 브라우저를 최대화한 상태로 테스트해 항상 통과했으나, CI는 headless 기본 해상도(1280x720)로 실행되어 Admin의 전체 선택 체크박스, PIM의 검색 필터 입력창이 반응형으로 숨겨져 요소를 찾을 수 없는 문제가 발생
- 원인 분석: 화면 크기에 따라 일부 UI 요소가 조건부로 렌더링/숨김 처리되는 반응형 구조였으나, 로컬에서는 항상 큰 화면으로 테스트해 이 분기를 가려서 인지하지 못함
- 해결: CI 환경에서 `viewport: { width: 1920, height: 1080 }`로 데스크톱 레이아웃을 명시적으로 고정하여, headless 여부와 무관하게 로컬과 동일한 레이아웃 조건을 보장
- 배운 점: "로컬에서 통과 = 신뢰 가능"이 아니라, 로컬 실행 조건 자체가 CI와 다르면 로컬 테스트가 오히려 잠재 결함을 가릴 수 있음. 이후로는 주요 변경 후 CI 환경과 유사한 조건(작은 뷰포트, headless)으로도 로컬에서 한 번씩 재현 테스트하는 습관을 추가

### 6. API 직접 호출 시 세션 인증 실패
- 문제: UI 로그인 직후 곧바로 API를 호출하면 401 응답을 받음. Playwright의 APIRequestContext, 브라우저 fetch 둘 다 동일하게 발생
- 원인 분석: 로그인 응답으로 세션 쿠키 자체는 즉시 설정되지만, 그 세션이 서버 사이드에서 완전히 유효화되기까지의 타이밍 차이로 추정. 로그인 직후 바로 API를 호출하면 이 타이밍에 걸림
- 해결: 로그인 후 페이지 이동(대시보드 도달)까지 명시적으로 대기 (`waitForURL`)한 뒤 API를 호출하도록 변경
- 배운 점: 세션 기반 인증에서는 "쿠키 존재 여부"와 "세션이 실제로 유효한 시점"이 다를 수 있음. UI 자동화에서 반복적으로 마주친 "비동기 완료 시점 명시적 확보"라는 원칙이 API 테스트에도 동일하게 적용됨

## 향후 개선 방향

- 목록 검색/필터 조합 테스트 확장 (현재는 단일 조건 위주)
- 크로스 브라우저(Firefox, WebKit) 실행 추가
- 환경변수 기반 설정을 여러 진입점이 공유하는 공통 설정 모듈로 통합
- 데이터 기반 테스트 범위를 다른 시나리오로도 확장
